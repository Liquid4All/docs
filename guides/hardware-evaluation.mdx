Use this guide when you are evaluating LFMs on a specific board, accelerator, mobile device, or server. The goal is to measure latency, throughput, memory behavior, and quantization trade-offs on the hardware you plan to ship.

<Tip>
[Pipette](https://pipette.liquid.ai/?utm_source=docs&utm_medium=hardware_evaluation&utm_campaign=pipette) has LFM speed and memory measured on real devices, filterable by quantization and runtime. Check it before profiling, then use this guide to measure on your own hardware.
</Tip>

## Recommended models

Start with [LFM3-1.7B](/lfm/models/lfm3-1.7b) for the current general text baseline. For initial board bring-up with very little memory, [LFM2.5-350M](/lfm/models/lfm25-350m) is a useful diagnostic model; its results do not characterize LFM3.

Profile the architectures your application will actually use:

1. **LFM3-1.7B**: current text, agents, and tool-use baseline.
2. **LFM3-VL-2B**, **LFM3-Audio-2B**, or **LFM3-Omni-2B**: the required modality, with its processor and encoders.
3. **LFM2.5-350M / 230M**: small-footprint bring-up and deployment alternatives.
4. **LFM2.5-1.2B-Instruct**: an older dense comparison point.
5. **LFM2.5-8B-A1B / 24B-A2B**: larger MoE alternatives, useful for measuring sparse-model behavior on your memory subsystem.

LFM3 combines short convolutions, sliding-window attention, and global attention. LFM2/LFM2.5 have a different convolution/attention layout. Measure memory, context scaling, prefill, and decode for each selected checkpoint; do not transfer an older architecture's results to LFM3.

## Quantization

LFMs are routinely deployed quantized on device. Major models ship pre-quantized, so choose the quantization level that fits your memory budget. Lower precision reduces memory and usually improves throughput.

- **GGUF ladder:** `Q4_0`, `Q4_K_M`, `Q5_K_M`, `Q6_K`, `Q8_0`, `F16`
- **MLX:** 4-bit, 5-bit, 6-bit, 8-bit, and bf16 repos per model
- **ONNX:** per-model `-ONNX` repos

`Q4_K_M` is the default recommendation for CPU and edge deployments. Move up the ladder if your quality bar requires it.

Profile at least two quantization levels, such as `Q4_K_M` and `Q8_0`, so you can see the memory, quality, and throughput trade-off on your hardware instead of measuring only one point.

## Benchmarking methodology

Report end-to-end latency with prefill and decode separated:

- Time to first token
- Decode tokens per second
- P50 and P95 latency, after one warmup iteration

Use these prompt and output lengths:

| Input tokens | Output tokens |
| --- | --- |
| 256 | 100 |
| 512 | 100 |
| 1024 | 100 |

Report peak memory at each context length:

- 256 tokens
- 512 tokens
- 1024 tokens
- 2048 tokens
- 4096 tokens

This gives you a clear view of scaling behavior, KV-cache efficiency, and deployment headroom.
