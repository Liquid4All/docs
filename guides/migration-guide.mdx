This guide is for teams already running Qwen, Llama, or Gemma who want to evaluate Liquid Foundation Models (LFMs) as replacements. LFMs load and serve through the same frameworks you already use, so most migrations are a model ID and configuration change. The details that usually matter are:
- deployment runtime choice (see [Deployment runtimes](#deployment-runtimes)),
- chat templates (see [Chat Template](#chat-template)),
- sampling configuration (see [Sampling Configuration](#sampling-configuration)),
- tool-call parsing (see [Tool Use](#tool-use)), and
- LoRA module names (see [Fine-tuning](#fine-tuning)).

Use this alongside [Use Case Evaluation](/guides/use-case-evaluation) for model selection and benchmarking methodology.

## Model mapping

Start with LFM3 for general text, vision, audio, or omni workloads. Compare models within your deployment's memory, latency, and quality constraints. Smaller and specialized older models remain useful when they fit those constraints better.

| If you run | Evaluate | Notes |
| --- | --- | --- |
| General text models, `1B-4B` | [LFM3-1.7B](/lfm/models/lfm3-1.7b) | Starting point for chat, local agents, tool use, and structured output; 256K context. |
| Vision-language models | [LFM3-VL-2B](/lfm/models/lfm3-vl-2b) | Image and video understanding, visual reasoning, and OCR. |
| Whisper plus separate TTS | [LFM3-Audio-2B](/lfm/models/lfm3-audio-2b) | ASR, TTS, and speech-to-speech in one model. |
| Separate vision and speech models | [LFM3-Omni-2B](/lfm/models/lfm3-omni-2b) | Text, image, video, and audio input with text or speech output. |
| Small text models, `<1B` | [LFM2.5-230M](/lfm/models/lfm25-230m) or [LFM2.5-350M](/lfm/models/lfm25-350m) | Classification, extraction, routing, and tight memory budgets. |
| Larger text models, `4B-13B` | [LFM2.5-8B-A1B](/lfm/models/lfm25-8b-a1b) | MoE alternative for reasoning and agentic workloads; 1.5B active parameters. |
| Larger text models, `14B+` | [LFM2.5-24B-A2B](/lfm/models/lfm25-24b-a2b) | Larger reasoning MoE alternative; evaluate quality, latency, and memory on your task. |

For image-to-JSON extraction, also evaluate the specialized [LFM2.5-VL-Extract models](/lfm/models/liquid-nanos).

See the [Complete Model Library](/lfm/models/complete-library) for the full catalog.

## Deployment runtimes

Across runtimes, avoid carrying over hand-written Qwen, Llama, or Gemma prompt templates. Use the model-provided chat template and a runtime build that supports your checkpoint. For tool use, LFM3 uses `qwen3_coder` parsing in vLLM and SGLang; LFM2 and LFM2.5 use `lfm2`. Follow the selected model's quickstart for the full launch configuration.

For GPU inference, see [Transformers](/deployment/gpu-inference/transformers), [vLLM](/deployment/gpu-inference/vllm), [SGLang](/deployment/gpu-inference/sglang), or [zml/llmd](/deployment/gpu-inference/zml-llmd).

For edge and on-device inference, see [llama.cpp](/deployment/on-device/llama-cpp), [Ollama](/deployment/on-device/ollama), [Atomic Chat](/deployment/on-device/atomic-chat), [LM Studio](/deployment/on-device/lm-studio), [MLX](/deployment/on-device/mlx), or [ONNX](/deployment/on-device/onnx). To embed a model in a mobile or desktop app, see [Build with llama.cpp](/deployment/on-device/llama-cpp/mobile).

## Chat Template

LFMs use a ChatML-style format, with generation-specific tokens and reasoning behavior. LFM3 templates normally open a thinking-model assistant turn with `<think>`; use the tokenizer or processor to format the prompt.

Roles are `system`, `user`, `assistant`, and `tool`. Image and video markers differ by model generation; let the processor insert them.

Migration notes:

- **From Qwen:** ChatML is familiar, but token details differ. Use `apply_chat_template`; do not reuse literal Qwen strings.
- **From Llama:** replace `<|begin_of_text|>` and `<|start_header_id|>` prompt builders.
- **From Gemma:** replace `<start_of_turn>` builders. LFMs support a real `system` role.

See [Chat Template](/lfm/key-concepts/chat-template) and Hugging Face's [`apply_chat_template` guide](https://huggingface.co/docs/transformers/main/en/chat_templating#using-applychattemplate) for the full formatting workflow.

Generation parameters are model-specific. Tune on your task instead of carrying over defaults from Qwen, Llama, or Gemma.

## Tool Use

LFM3 emits XML tool calls, using a superset of the `qwen3_coder` format:

```text
<tool_call>
<function=get_candidate_status>
<parameter=candidate_id>
12345
</parameter>
</function>
</tool_call>
```

LFM2 and LFM2.5 use the earlier tool-call format, typically a Pythonic call list:

<ToolCallTokenExample></ToolCallTokenExample>

Serving runtimes can parse these native formats into OpenAI-compatible `tool_calls`. A client that reads raw generated text must handle the format for its selected model.

What to do:

1. Pass tools through [`tokenizer.apply_chat_template(messages, tools=[...])`](https://huggingface.co/docs/transformers/main/en/chat_templating#using-applychattemplate) or the serving runtime's supported tool mechanism.
2. Prefer the serving runtime's structured `tool_calls`. If you parse raw text, handle LFM3 XML or the older `<|tool_call_start|>` / `<|tool_call_end|>` format as appropriate.
3. On vLLM or SGLang, use `qwen3_coder` for LFM3 and `lfm2` for LFM2/LFM2.5, with the other flags from the model's quickstart.
4. Return results as `tool` role messages, with JSON content if useful.
5. If you fine-tune for tool calling, format the data with the selected model's own chat template and native tool-call format.

See [Tool Use](/lfm/key-concepts/tool-use) for the full tool-calling workflow.

## Fine-tuning

Use a training workflow that supports your model architecture. The [LFM3-1.7B model card](https://huggingface.co/LiquidAI/LFM3-1.7B#fine-tuning) documents a TRL path. Check framework support before reusing an older training recipe.

First, choose LoRA `target_modules` for the selected model. Inspect `model.named_modules()` or use its training recipe; module names differ across LFM generations. The following example applies to LFM2 and LFM2.5 only:

```python
# LFM2 / LFM2.5
target_modules = ["w1", "w2", "w3", "q_proj", "k_proj", "v_proj", "out_proj", "in_proj"]

# These Llama/Qwen/Gemma module names do not apply to this LFM2/LFM2.5 recipe:
# o_proj/gate_proj/up_proj/down_proj do not exist.
```

Before a long run, call `model.print_trainable_parameters()`. You should see millions of trainable parameters, and the LoRA module count should be in the expected range for your model size. If it is near zero, the module names are wrong.

Second, format training examples with the LFM chat template. Training data formatted with your previous model's template creates a silent distribution mismatch.

Use [Liquid Finetune](/lfm/fine-tuning/liquid-finetune), [TRL](/lfm/fine-tuning/trl), [Unsloth](/lfm/fine-tuning/unsloth), or [Halo](/lfm/fine-tuning/halo) according to the selected model and the framework's documented support.

See [Fine-tuning Overview](/lfm/fine-tuning/overview) for the main fine-tuning workflow.
