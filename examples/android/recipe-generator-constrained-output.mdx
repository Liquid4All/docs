RecipeGenerator uses **LFM2.5-1.2B-Instruct**, Q5_K_M, to generate a recipe as JSON. llama.cpp converts the recipe schema into a grammar that constrains generation.

## Environment setup

Use Android Studio with JDK 17, Android SDK 36, NDK `29.0.13113456`, and CMake `3.31.6`. The projects pin Kotlin `2.3.20` and llama.cpp `v0.9.0`.

Clone the complete repository so the app can include `examples/android-common` and its pinned llama.cpp submodule:

```bash
git clone --recurse-submodules https://github.com/Liquid4All/cookbook.git
```

The shared runtime handles model downloads, native inference, cancellation, and cleanup. Keep the app and `android-common` directories together.

## How to run it

1. Open `cookbook/examples/RecipeGenerator` in Android Studio and run it on Android 12+.
2. On launch, the app downloads the model if needed (about 850 MB), then generates a dinner recipe automatically.
3. Read the recipe's name, ingredients, cooking time, vegetarian flag, and steps.
4. Tap **Generate another recipe** for another result, or **Retry** after a failure.

The current app uses the fixed prompt `A recipe for a dinner dish`. It has no ingredient-entry field; add one if your application needs user-selected dishes.

## Code walkthrough

The data class and schema in `MainActivityViewModel.kt` describe the same five fields:

```kotlin
@Serializable
data class Recipe(
    val name: String,

    val ingredients: List<String>,

    val cookingTime: Int,

    val isVegetarian: Boolean,

    val steps: List<String>,

)

// JSON schema for Recipe. llama.cpp turns it into a grammar, so the model can only generate matching JSON.
private const val RECIPE_SCHEMA = """
{
  "type": "object",
  "additionalProperties": false,
  "description": "A recipe for cooking great dishes",
  "properties": {
    "name": { "type": "string" },
    "ingredients": { "type": "array", "items": { "type": "string" }, "description": "Ingredients for making the dishes" },
    "cookingTime": { "type": "integer", "description": "Cooking time in minutes" },
    "isVegetarian": { "type": "boolean", "description": "Whether the meal is vegetarian" },
    "steps": { "type": "array", "items": { "type": "string" }, "description": "Steps of cooking" }
  },
  "required": ["name", "ingredients", "cookingTime", "isVegetarian", "steps"]
}
"""
```

`MainActivityViewModel` selects the model, supplies the schema to the runtime, and decodes only a successfully completed response:

```kotlin
class MainActivityViewModel(application: Application) : TextTaskViewModel(
    application, Models.text,
    "You are a recipe generator. Generate JSON that follows this schema: $RECIPE_SCHEMA",
    RECIPE_SCHEMA,
) {
    var recipeState: Recipe? by mutableStateOf(null)
        private set

    fun generateRecipe() { generate("A recipe for a dinner dish") }
    override fun completed(output: String) {
        recipeState = Json.decodeFromString<Recipe>(output)
    }
}
```

The native implementation is in `examples/android-common/src/main/cpp/text_jni.cpp`. It applies the checkpoint's chat template, converts the JSON schema to a grammar, and streams UTF-8 output. Cancellation and token/context limits produce an error instead of treating an unfinished document as a valid recipe.

## Results

The app renders this structure:

```json
{
  "name": "Vegetable pasta",
  "ingredients": ["200 g pasta", "1 zucchini", "1 tbsp olive oil"],
  "cookingTime": 20,
  "isVegetarian": true,
  "steps": ["Cook the pasta.", "Sauté the zucchini.", "Combine and serve."]
}
```

Schema constraints enforce the output shape; they do not validate the recipe's content. This is an illustrative recipe, not a recorded model response. To extend the structure, update the data class, JSON schema, and renderer together.

## Downloads and lifecycle

The first request downloads the model from Hugging Face. Downloads go to a temporary file; the runtime checks the expected size and SHA-256 before publishing the final GGUF. An interrupted download restarts on the next attempt. A verified cached model works offline.

A ViewModel retains the model across screen rotation. Native calls run in one queue per model instance. Cancellation stops the token loop before cleanup releases the model. A failed request displays an error and allows retry.
