Start with [LFM3-1.7B](/lfm/models/lfm3-1.7b) for new text applications. Speculative decoding can speed up generation: a small **draft model** proposes several tokens ahead, and the **target model** verifies them together. A drafter must match the target model and be supported by the inference engine; an LFM2.5 drafter cannot be reused with LFM3.

## LFM3 speculative decoding

LFM3-1.7B has a community-maintained [DSpark drafter](https://huggingface.co/rasyosef/LFM3-1.7B-DSpark) and [GGUF sidecar](https://huggingface.co/rasyosef/LFM3-1.7B-DSpark-GGUF). These are community checkpoints, not official LiquidAI releases. LiquidAI's official DSpark releases currently cover the LFM2.5 targets listed below.

With a recent llama.cpp build, run the LFM3 target with its matching drafter:

```bash
llama serve -hf LiquidAI/LFM3-1.7B-GGUF:Q4_K_M \
  -hfd rasyosef/LFM3-1.7B-DSpark-GGUF:F16 \
  --spec-type draft-dspark --spec-draft-n-max 8 --spec-draft-n-min 0 \
  -c 4096 -ngl 99 -ngld 99 -fa on \
  --temp 0.1 --top-k 50 --repeat-penalty 1.1
```

This target/drafter pair was checked with llama.cpp b12359 on Apple silicon and accepted drafted tokens. Check that `llama serve --help` lists `draft-dspark`. The drafter's [model card](https://huggingface.co/rasyosef/LFM3-1.7B-DSpark#usage) also documents a vLLM integration with additional requirements; the SGLang and MLX-VLM recipes below are for LFM2.5, not this LFM3 drafter.

Measure speed and output behavior with your own prompts. A compatible drafter does not guarantee a speedup, and numerical differences can change generated text; see the [output FAQ](#faq).

## FAQ

<AccordionGroup>

<Accordion title="Does speculative decoding change the model's output?">
  The target verifies the proposed tokens. An exact speculative sampler is designed to preserve the target's sampling distribution, but implementation details and floating-point differences can change a particular generated sequence, including with greedy decoding. In our quantized LFM3 llama.cpp smoke test, two of three greedy responses matched the baseline exactly and one diverged. Validate output behavior as well as latency with your target, drafter, quantization, and runtime.
</Accordion>

<Accordion title="What speculative decoding methods are supported for LFMs?">
  This page documents DSpark: the community LFM3 drafter and LiquidAI's official LFM2.5 drafters in [Available draft models](#available-draft-models). Other methods require their own compatible checkpoints and runtime support; selecting an engine flag alone does not add support. These LFM checkpoints do not include MTP heads, so vLLM's `--speculative-config` with `"method": "mtp"` does not work with them.
</Accordion>

<Accordion title="Why is the speedup smaller with quantized models?">
  DSpark gives the largest speedup with 16-bit (F16 or BF16) target models. With a quantized target, such as Q4, each verification step costs more, so the speedup is much smaller. On CPUs and Apple silicon, a quantized target may give little or no speedup.

  Quantizing the drafter has little effect on speed. For the best results, run a 16-bit target. If you need a quantized target to fit in memory, measure the speedup on your own hardware first.
</Accordion>

</AccordionGroup>
